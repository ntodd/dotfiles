Employee event sign-ups, walked through

The RFC runs 680 lines. This page covers the same ground in the order you'd want to learn it: what problem it solves, how one event moves through time, how the database settles a race at 9:00:00, and what the admin side looks like. The interactive parts let you poke at the tricky bits.

Status: Proposed Seventh draft, 2026-10-14 New context: Pulse.Signups One new dep: nimble_csv

01The story in three beats

Weigand hands out limited things to employees: Komets season tickets, TinCaps seats, volunteer spots. Today it's email plus a spreadsheet, and "first reply wins" is enforced by whoever happens to be reading the inbox. When something popular drops, a flood of replies arrives at once and the outcome is hard to defend.

BEFORE

HR sets it up

Creates "2026-2027 Komets Hockey", uploads a CSV of 36 game dates, picks the eligible roles, sets preview, open, and close times. Places holds on six games for executives.

9:00:00

Employees pick

The page flips from countdown to open on its own. Each eligible employee claims one game. Postgres decides who got there first. Losers get "Someone just claimed that one."

FRIDAY 5 PM

It closes

Every claimant gets one email with their game, seats, and pickup instructions. HR gets a report with CSV export.

The rule that shapes everything One slot (game date) goes to exactly one employee, and each employee gets one slot per event. The four tickets on Dec 31 are one family's night out, not four separate seats. Both rules live in Postgres unique indexes, so no LiveView bug can break them.

02The pieces

Four nouns and two kinds of people. Once these click, the rest of the RFC reads easily.

Event

The thing being handed out

Title, rich-text description (Quill, like posts), pickup instructions, eligible roles, and three times: previews_at, opens_at, closes_at.

Slot

One game date

Start time, label ("vs. Toledo Walleye"), optional ticket count, location, details ("Sec 104 Row F"). Has no stored status.

Claim

An employee took a slot

Never deleted. Releasing sets released_at. source is self, admin, or held.

Hold

A claim for nobody

A claim row with user_id = NULL and a required note ("Exec: client entertainment"). Looks like "Taken" to employees.

Employee

Active user (service_account_enabled) in the same organization who holds at least one of the event's roles. Same join shape as Posts.post_accessible_to_user?/2. Admins are not automatically eligible to claim.

Event manager

is_admin or the new is_event_coordinator. Runs events, holds, assignments, releases, and the report. Coordinators can't see any other admin page.

03An event's life

Only status is stored (draft, published, closed, archived). Whether claiming is open comes from status plus the clock. Drag the slider or click a phase to see what an employee would get at that moment.

Why a 404 and not "not allowed"? Before previews_at, and for anyone outside the roles, the event page returns the exact same 404 as a made-up id. A leaked or guessed URL reveals nothing, including the event's title.

The countdown runs on Process.send_after(self(), :opened, ms) in the LiveView, so the page flips with no reload. The server never trusts that timer: ensure_open/2 re-checks server time inside the claim transaction. A click a few ms early because of node clock skew just gets "Sign-ups open at 9:00" and can retry.

Reviewer notenitLifecycle table vs. holds.

The RFC's Draft row lists "admin assign allowed" but not holds, while Decision 11 says holds can be placed at any time. Probably a table omission. The slider above follows Decision 11.

04The 9:00 flood

This is the heart of the RFC. A claim is one INSERT into signup_claims. Two partial unique indexes guard it. When two transactions try to insert the same key, Postgres makes the second one wait on the first's uncommitted index entry, then decides based on whether the first commits or rolls back. Whoever commits first wins. That's FCFS, enforced by the database.

The code, trimmed

def claim_slot(%User{} = user, slot_id) do
  Repo.transaction(fn ->
    slot = Repo.get!(Slot, slot_id) |> Repo.preload(:event)
    with :ok <- ensure_open(slot.event, DateTime.utc_now()),
         :ok <- ensure_eligible(slot.event, user),
         {:ok, claim} <- insert_claim(slot.event, slot, user, source: :self) do
      claim
    else
      {:error, %Ecto.Changeset{} = cs} -> Repo.rollback(claim_error(cs, user, slot))
      {:error, reason} -> Repo.rollback(reason)
    end
  end)
  |> tap(&broadcast_after_commit/1)
end

The context never asks "is this slot free?" first. That answer could be stale by the time the insert runs. The LiveView may grey out taken slots for UX, but only the insert decides.

Reviewer notecheckDouble-click lookup runs inside an aborted transaction.

claim_error/3 is supposed to notice "this slot's active claim is already mine" and return {:ok, existing_claim}. It runs after the failed INSERT, still inside Repo.transaction. Once a statement errors, Postgres aborts the transaction and any further query in it fails. The lookup has to happen after the rollback, outside the transaction.

Reviewer notecheckSame user, same slot can trip either index.

A double click on one game conflicts on both ..._per_slot and ..._per_user. Which one Postgres reports isn't something to rely on, so the "it's already mine" check should run for both :slot_taken and :already_claimed.

Reviewer notenitRepo.get! on a client-supplied slot id.

A bad or deleted id raises inside the transaction. Users still can't claim across events by guessing ids, but the failure is a LiveView crash instead of a clean not-found.

ResultWhat the employee sees
{:ok, claim}"You're going: Dec 31 vs. Toledo Walleye"
{:error, :slot_taken}"Someone just claimed that one. Pick another."
{:error, :already_claimed}"You already have {their slot}."
{:error, :not_open}"Sign-ups open at {opens_at}." or "Sign-ups are closed."
{:error, :not_eligible}Treated as not found; redirect to /events

Before any of this, a client-side confirm modal (pure JS commands, no round trip) names the slot and the one-per-event rule. A claim is final for the employee, so a misclick shouldn't lock someone into the wrong game.

05Two indexes do the work

CREATE UNIQUE INDEX signup_claims_one_active_per_slot
  ON signup_claims (slot_id) WHERE released_at IS NULL;

CREATE UNIQUE INDEX signup_claims_one_active_per_user
  ON signup_claims (event_id, user_id) WHERE released_at IS NULL;

Partial = history for free

Releasing a claim sets released_at, which drops the row out of both indexes. The slot opens, the employee can pick again, and the old row stays for the report.

The name tells you which rule

claim_error/3 maps ..._per_slot to :slot_taken and ..._per_user to :already_claimed. No extra query to figure out what went wrong.

Holds slip past the user rule

Postgres treats NULLs as distinct in unique indexes. Holds have user_id = NULL, so any number of them coexist in one event. They still take their slot through the per-slot index. The RFC forbids NULLS NOT DISTINCT for this reason.

A check constraint keeps hold rows honest:

CHECK ((source = 'held') = (user_id IS NULL)
   AND (source <> 'held' OR note IS NOT NULL))

Read it as: a hold has no user and must have a note; every non-hold has a user.

Why not a capacity counter? The first draft had capacity and claimed_count with a conditional UPDATE. Tickets here go to one family per date, so the counter was a denormalized column that could drift, serving a case nobody asked for. If shared-date events show up (volunteer shifts), model them as several slots on one date or add capacity back then.

06Data model

Four new tables plus one column on users. All binary_id keys and timestamps(). Hover or focus a column for the RFC's note on it.

Slots have no status column. A slot is taken when it has an active claim, open otherwise, so there's nothing to keep in sync. slot_id and user_id on claims are on_delete: :restrict, so deleting a slot with history, or ever hard-deleting a user, fails loudly instead of punching holes in the report.

07Live updates

Every employee page subscribes to "signup_event:#{event_id}" on Pulse.PubSub. After a claim or release commits, the context broadcasts {:slot_changed, slot_id, :taken | :open} and each LiveView updates that one slot in a stream. Admin edits broadcast {:event_changed, event_id} and pages reload the event.

1. CommitAlice's INSERT commits in Postgres
→
2. Broadcast{:slot_changed, id, :taken} across the DNSCluster
→
3. PatchEvery open page flips that game to "Taken" within a second
PubSub is a courtesy If a broadcast is lost (cluster split, node restart), a page may show a taken slot as open. Clicking it returns :slot_taken and the page corrects itself. Correctness never depends on the broadcast (OR2).

Volume: 300 claims × 300 open pages ≈ 90,000 small deliveries over the first minute.

08Who's viewing

The event page shows a "Viewing now" strip of profile photos so people can watch the room fill up before 9:00. It uses PulseWeb.Presence on a separate topic, "signup_event_viewers:#{event_id}", keyed by user.id so three tabs count once. Photo URL is computed at track time, so rendering costs no queries.

At 8:59 hundreds of people join within seconds and every join sends a diff to every viewer. The LiveView applies diffs to an assign and re-renders the strip at most once per second. Toggle the throttle off to see how many renders that saves.

Privacy rules

  • Presence meta carries only name, email, and photo URL. Claiming never updates it.
  • No badge, ring, or ordering hints at who has claimed. The viewers modal lists names alphabetically, not by join order.
  • Slot rows show Claim, Taken, Yours, or Not open yet. "Yours" only for your own claim. Held slots look identical to taken ones.
  • Copy says "Viewing now" or "Here with you", never "Waiting to claim".

The RFC admits someone could infer a claim if a viewer leaves right after a game turns taken. It doesn't try to prevent that, only to avoid making it easier.

09Admin tools

Management lives at /admin/events in a new :event_admin live_session. Three actions change who has a slot:

hold_slots/3

Hold

Check several open slots, enter a required note, click Hold. One transaction, all or nothing. If any slot was already taken, it rolls back and returns {:error, {:slots_taken, ids}} so the admin can deselect and retry.

Skips the time window and eligibility (no user to check). Sends no email, ever.

assign_slot/3

Assign

Runs the normal claim algorithm with source: :admin. Skips the time window, so it works in draft and before opening (the superintendent who can't be at a desk at 9:00). Still requires eligibility and both indexes.

release_claim/3

Release

Locks the claim row FOR UPDATE, refuses a double release, sets released_at, released_by_id, and a required reason. Works the same for holds. The slot reopens on every page.

Employees can't release their own claim Decision log 1: they ask an event manager. This stops people from releasing and re-picking to game the system.

The report

/admin/events/:id/report has a summary (eligible users, active claims, held slots counted separately, open slots, releases), one row per slot in date order with claimant or "Held: note", a Released section with reasons, and a collapsed "Eligible, no claim" list for follow-up next time.

CSV export is a controller at GET /admin/events/:id/report.csv. Here's a detail worth knowing: the /admin router scope only requires authentication for controller routes today, not admin. So the RFC adds a :require_event_manager plug that 404s anyone else. Fixing the existing ImageController exposure is listed as future work.

10CSV slot import

HR downloads a static template, fills in the season in Excel, saves as CSV, uploads. The file is consumed locally (not sent to S3), parsed by Pulse.Signups.SlotImport.parse/1, previewed with per-row errors, and saved in one insert_all only if every row is valid.

date,time,label,ticket_count,location,details
10/17/2026,7:30 PM,vs. Toledo Walleye,4,Allen County War Memorial Coliseum,Sec 104 Row F
10/24/2026,7:30 PM,vs. Kalamazoo Wings,4,Allen County War Memorial Coliseum,Sec 104 Row F

Most of the parsing rules exist because Excel does odd things:

Encoding

Strip the UTF-8 BOM ("CSV UTF-8"). If it isn't valid UTF-8, treat it as Windows-1252 (plain "CSV Comma delimited"). Normalize \r\n and old Mac \r.

Headers

Case-insensitive, any order. date and label required. Unknown columns ignored, so HR can keep a notes column.

Dates

M/D/YYYY, YYYY-MM-DD, and Excel serial numbers like 46312 when a column got formatted as a number.

Times

h:mm AM/PM, HH:MM, or blank. Blank means all_day = true at local midnight. Read as America/Indiana/Indianapolis, stored as UTC.

Row numbers

Errors use spreadsheet rows (header = row 1): Row 14: time "7:30" needs AM or PM. Fully blank trailing rows are skipped.

Duplicates

Same date + time + label as an existing slot or another row is an error, so uploading the same file twice does nothing.

The report export uses the same NimbleCSV module with a UTF-8 BOM so Excel shows accented names correctly.

11Who can do what

A new Pulse.EventCoordinator app role, mapped by GUID in postern's static config (same as Pulse.Admin), lets HR run events without full admin. Renaming the role in the Entra portal can't change access. If PULSE_EVENT_COORDINATOR_ROLE_ID is unset, only admins manage events.

Wiring: replace_postern_roles/2 pulls the coordinator name out before matching DB roles and sets users.is_event_coordinator. InitAssigns gets an :event_admin kind; the existing :admin kind is unchanged. Every management function in Pulse.Signups also checks manager?/1 and returns {:error, :unauthorized}, so a mounted socket whose user lost the role can't keep writing. Coordinators reach the pages through a "Manage events" link in the user nav, since they can't open /admin.

12Emails go out at close, not at claim

The window may stay open for days, during which admins release and reassign. An email sent at 9:00:01 could be wrong by Friday. So the employee page is the confirmation while it's open, and everyone gets one final email when it closes. Side benefit: no email burst during the flood.

Close happensManual close_event/2, or a job scheduled at closes_at (unique on event_id; moving closes_at reschedules it)
→
SignupCloseNotifierBails if the event isn't actually closed yet. Selects active claims with a user and notified_at IS NULL. Holds skipped.
→
SignupClaimNotifier × NOban.insert_all, one per claim, kind confirmed. Skips released claims, sends, sets notified_at.

After the close

An admin assign or release emails the affected employee right away (assigned / released kinds). Before close, admin changes send nothing, because the close email covers the final state.

Reopen

reopen_event/2 sets published and clears closed_at. Claims already emailed keep notified_at, so only new claims get emailed at the next close.

No automatic email when a slot's date or label changes (Decision log 7). The admin page warns the manager to tell claimants themselves.

Reviewer notegapReopen doesn't say it re-enqueues the close job.

After a close, the scheduled SignupCloseNotifier has already run. reopen_event/2 with a future closes_at needs to schedule a new one, or the event never closes on its own again. "Publishing or changing closes_at" covers it only if reopen counts as one of those.

Reviewer notecheckManual close vs. the scheduled unique job.

Manual close enqueues SignupCloseNotifier while a scheduled one for the same event_id may already exist. With unique + replace: [scheduled: [:scheduled_at]], the insert likely moves the existing job to now, which is fine. Confirm that against Oban Pro's unique semantics and cover it in a worker test.

Reviewer notenitScheduled close doesn't set status.

The close job sets closed_at but leaves status = published. The lifecycle table handles this through time, but it means "closed" has two representations. Fine if intentional; the RFC should say so.

13Load and risks

Claims

Each holds a connection for a few ms. Pool of 10 per node across several nodes: 300 claims clear in well under a second. 100 people on the New Year's Eve game queue on one index entry for about a ms each; 99 get :slot_taken. Target: p95 under 20 ms (OR1).

Postern / Graph

Every load goes through postern, which refreshes roles from Graph on cache expiry. Everyone arriving at 9:00 means a burst of Graph calls. The countdown page encourages people to show up early, which spreads it out.

Deploys

A deploy drops every socket during the moment people care about most. Rule: no deploys within an hour of an opens_at. The admin dashboard SHOULD show upcoming openings.

Clock skew

ECS nodes may open a few hundred ms apart. Early clicks get :not_open and retry. NTP keeps it small.

Policy risks the RFC calls out

  • FCFS favors desk workers. Field staff may miss every popular game. Admin assignment is the release valve; a lottery is the likely next step.
  • Holds are invisible to employees. By design. If execs hold all the best dates, people will notice anyway. The report makes it auditable.
  • Role churn. Someone who changes departments after claiming keeps their claim. Eligibility is checked at claim time only.
  • Coordinator removal lags Entra by the postern roles_ttl_ms, same as admin today.

14Roads not taken

Slot capacity with a claim counter

Supports shared dates, but tickets go to one family per date. A drifting denormalized counter plus a CHECK and capacity-edit code path for a case nobody needs.

SELECT ... FOR UPDATE on the slot row

Correct, but holds a lock across round trips and puts the rule in Elixir. The partial index enforces the same rule in one statement and also covers inserts that bypass the context.

Queue claims through Oban or a GenServer

Natural ordering, but a single point of failure, cross-node routing, and a reply path to the LiveView. Postgres already serializes conflicting writes and survives restarts.

Lottery instead of FCFS

Fairer to field staff and removes the flood. Not what was asked for, and needs ranking, a draw, and result notification. Left as future work with an allocation column.

Reuse posts as the container

Free roles and editor, but posts carry feed semantics (display date, category, reactions, drafts), and editing a post's roles would silently change who's eligible.

Testing approach

The Ecto sandbox runs each test in one transaction on one connection, so concurrent Tasks get serialized and can't reproduce a real race. Since the guarantees come from Postgres anyway, tests hit the constraints directly: insert a second active claim and assert the right violation. An optional @tag :concurrency stress test checks out real connections and fires 200 claims at one slot, expecting exactly one success.

Rollout

Two additive migrations, no backfill, no feature flag (nothing is visible until someone publishes). Ops work before the first event: create the app role on each edge registration, set PULSE_EVENT_COORDINATOR_ROLE_ID in the ECS task definition, assign HR in Entra. Watch AppSignal for claim transaction time and any raw Ecto.ConstraintError.
